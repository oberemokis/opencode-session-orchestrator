# Настраиваемые маршруты и обязательные опросники

Проектное описание формата маршрута для OpenCode Orchestrator. Устройство runtime, статусы задачи, исходы этапа и модель защиты описаны в [архитектуре](architecture.md), здесь только то, что пишет пользователь. Цель: пользователь составляет процесс под свой проект, а харнес исполняет именно эту версию процесса даже после закрытия окон и перезапуска.

## Что умеет первая поставка

Ниже описан целевой формат. Первая поставка ([план](first-delivery.md)) читает только `.orchestrator/workflows/default.json`, встроенного маршрута нет, и загрузчик знает только эти поля; любое другое поле отклоняет `/orchestrate` с путём к нему:

```json
{
  "schemaVersion": 1,
  "id": "default",
  "stages": [
    { "id": "code", "uses": "code", "model": { "providerID": "openai", "id": "gpt-5.6-luna", "variant": "low" } },
    { "id": "show", "uses": "show" },
    { "id": "deliver", "uses": "deliver", "delivery": { "type": "local-commit" }, "on": { "failed": "goto:code" } }
  ]
}
```

| Поле этапа | Что значит |
| --- | --- |
| `id`, `uses` | Виды только `code`, `show`, `deliver` |
| `model` | Объект `{providerID, id, variant?}`, профилей `models` и `defaultModel` пока нет. Без `model` сессия работает на модели по умолчанию. Runtime сверяет пару со списком моделей OpenCode до задания; неизвестная модель даёт `blocked` |
| `instructions` | Текст, который добавляется к заданию этапа |
| `on` | Исходы: у `code` это `passed`, `stuck`, `stalled`; у `show` `passed` и `changes-requested`; у `deliver` `passed` и `failed`. Действия `next`, `repeat`, `stop`, `escalate`, `goto:<id>` |
| `limits` | `retries` (по умолчанию 2) и `stallMinutes` (по умолчанию 30) |
| `delivery` | Только у `deliver`, только `{"type": "local-commit"}` |

Рядом лежит необязательный `.orchestrator/config.json` с настройками проекта:

```json
{
  "base": "main",
  "branchPrefix": "orchestrator",
  "setup": { "copy": [".env.local"], "command": "pnpm install --frozen-lockfile" },
  "deny": ["*npm publish*", "*deploy*"],
  "mcpRead": ["YouTrack_get_issue", "gitlab_get_merge_request"]
}
```

`base` это ветка или коммит, от которого растёт ветка задачи (по умолчанию `HEAD` главного checkout). `setup.copy` копирует файлы из главного checkout в свежий worktree, `setup.command` выполняется в нём до создания сессии. `deny` дописывает шаблоны shell к общему списку запретов. `mcpRead` перечисляет MCP-инструменты в виде `<сервер>_<инструмент>`, которые исполнителю разрешены; остальные MCP-инструменты закрыты. Оба файла runtime читает из главного checkout на `/orchestrate` и хранит снимок в задаче: правка файла не меняет идущую задачу.

## Как пользователь задаёт процесс

Маршрут лежит в `.orchestrator/workflows/<имя>.json` в репозитории проекта. Один файл описывает один маршрут; формат принадлежит харнесу, не `opencode.json`. Редактор подсказывает поля по JSON Schema, её выдаёт `opencode-orchestrator workflow schema`. `fleet-v1` остаётся встроенным маршрутом по умолчанию. Исследовательский маршрут может закончиться отчётом без коммита и MR.

Пример маршрута для команды, которая перед кодом согласует план, после тестов отдельно проверяет доступность интерфейса, а затем передаёт одобренный дифф на доставку. Имена моделей иллюстративные: профиль должен пройти проверку по каталогу конкретной установки.

```json
{
  "schemaVersion": 1,
  "id": "feature-with-accessibility",
  "models": {
    "fast": { "provider": "openai", "model": "gpt-6.1-sol", "variant": "low" },
    "careful": { "provider": "openai", "model": "gpt-6.1-sol", "variant": "high" }
  },
  "defaultModel": "fast",
  "stages": [
    { "id": "research", "uses": "research" },
    {
      "id": "design",
      "uses": "plan",
      "model": "careful",
      "after": {
        "title": "Согласовать план",
        "preview": "stage.result",
        "fields": [
          {
            "id": "decision",
            "type": "choice",
            "label": "Что делать с этим планом?",
            "required": true,
            "options": [{ "id": "accept", "label": "Перейти к реализации" }, { "id": "revise", "label": "Переработать план" }]
          },
          {
            "id": "notes",
            "type": "textarea",
            "label": "Что изменить в плане?",
            "visibleWhen": { "field": "decision", "equals": "revise" },
            "requiredWhen": { "field": "decision", "equals": "revise" }
          }
        ]
      },
      "on": {
        "after.decision.accept": "next",
        "after.decision.revise": "repeat"
      }
    },
    { "id": "implement", "uses": "code", "model": "careful" },
    { "id": "review", "uses": "review", "model": "careful", "on": { "failed": "goto:implement" } },
    { "id": "test", "uses": "verify", "on": { "failed": "goto:implement" } },
    {
      "id": "accessibility",
      "uses": "research",
      "title": "Проверка доступности",
      "instruction": "Проверь клавиатурную навигацию и подписи элементов. Приложи список проверок и находок.",
      "when": { "changedFilesUnder": "src/ui" },
      "before": {
        "title": "Объём проверки доступности",
        "fields": [
          {
            "id": "flow",
            "type": "text",
            "label": "Какой пользовательский сценарий проверить в первую очередь?",
            "required": true
          }
        ]
      }
    },
    {
      "id": "keyboard-qa",
      "uses": "manual-test",
      "executor": { "type": "agent", "browserMcp": "browse" },
      "model": "careful",
      "title": "Ручная проверка формы",
      "scenarios": [
        {
          "id": "save-by-keyboard",
          "steps": "Измени значение поля. Клавишей Tab перейди к кнопке «Сохранить» и нажми Enter. Обнови страницу.",
          "expected": "После обновления страницы в поле осталось новое значение."
        }
      ],
      "on": { "failed": "goto:implement" }
    },
    { "id": "show", "uses": "show", "on": { "changes-requested": "goto:implement" } },
    {
      "id": "publish",
      "uses": "deliver",
      "delivery": { "type": "gitlab-mr", "project": "group/app", "target": "main" },
      "on": { "ci-failed": "goto:implement", "changes-requested": "goto:implement" },
      "limits": { "retries": 2 }
    }
  ]
}
```

Чтобы дважды провести ревью разными моделями, пользователь добавляет два элемента с `uses: "review"`, разными `id` и профилями `model`. Чтобы добавить проверку локализации, достаточно нового `research` со своей инструкцией и вопросами. Если требуется новая операция (например, загрузка сборки в новый реестр), одного текста недостаточно: нужен обработчик в runtime, который умеет выполнить её и проверить результат. После регистрации обработчика его можно выбирать в любом маршруте.

## Что означает этап

`id` обозначает место в маршруте, `uses` выбирает вид этапа. Вид определяет исполнителя, разрешённые действия, результат и возможные исходы; таблица видов приведена в [архитектуре](architecture.md#виды-этапа). Конфиг задаёт порядок, инструкцию, модель, вопросы и реакции на исходы. Он не содержит исполняемого JavaScript и не расширяет права вида.

Этапы идут последовательно, активен один. Успех ведёт к следующему элементу, успех последнего завершает маршрут. `before` блокирует запуск этапа, `after` блокирует принятие его результата. Маршрут, допускающий `deliver` без `show` по актуальному диффу, отклоняется; перед самой доставкой runtime заново сверяет фактический дифф с `reviewedDiff`. Ответ «да» на вопрос о доступности `reviewedDiff` не присваивает.

## Переходы: карта `on`

Все переходы задаёт одна карта `on` у этапа. Ключ это исход этапа или выбор в анкете, значение это действие.

| Ключ | Когда срабатывает |
| --- | --- |
| `passed`, `failed`, `changes-requested`, `stuck`, `stopped` | Исход прохода этапа. `changes-requested` дают `show` и ревью MR, `stuck` выставляет runtime при отсутствии движения или когда исполнитель не может продолжить |
| `ci-failed` | На `deliver` CI упал для ожидаемого SHA |
| `before.<поле>.<вариант>`, `after.<поле>.<вариант>` | В анкете выбран вариант обязательного поля `choice` |

Действия: `next`, `repeat`, `stop`, `goto:<id>`, `escalate`. `repeat` начинает новый проход того же этапа с замечаниями из анкеты; у прохода свой `stageRunID`, прежние анкеты остаются в истории. `escalate` открывает человеку вопрос с причиной и вариантами продолжить, повторить или остановить.

Значения по умолчанию: `passed` и валидная отправка анкеты без своего ключа ведут к следующему шагу, остальные исходы к `escalate`. Если у встроенного вида единственная разумная цель возврата (например, `show` → последний `code`), загрузчик может вывести её сам и показать в развёрнутом маршруте.

Автоматический возврат назад считается повтором. `limits.retries` (по умолчанию 2) ограничивает повторы одного этапа, при исчерпании действие заменяется на `escalate`. `limits.stallMinutes` задаёт, через сколько минут без движения в логе сессии этап получает исход `stuck`. Возврат по выбору человека в лимит не входит.

## Какие поля можно настроить у этапа

| Поле | Как влияет на выполнение |
| --- | --- |
| `title`, `instruction` | Заголовок в списке задач и текст задания исполнителю |
| `model` | Ссылка на профиль из `models`; без неё применяется `defaultModel` |
| `before`, `after` | Обязательные анкеты до начала и после результата |
| `on`, `limits` | Переходы по исходам и ограничения повторов и зависания |
| `inputs`, `outputs` | `outputs` описывает, что этап обязан сдать; `inputs` ссылается на выходы предыдущих этапов. Пока обязательного выхода нет, этап не завершён |
| `when` | Условие запуска. В первой версии только `{ "changedFilesUnder": "<путь>" }`. Ложное условие пропускает этап с записью причины; если данных нет, решение откладывается |
| `sources` | MCP-подключения этапа и их обязательность. Недоступность обязательного источника не считается пустым результатом |
| `skills` | Скиллы с инструкциями по работе. Скилл не расширяет права вида: скилл ревью не даёт менять код |
| `executor`, `scenarios` | Только для `manual-test` |
| `delivery` | Только для `deliver`: `local-commit` или `gitlab-mr` с проектом и целевой веткой |

## Модель и effort

`models` задаёт именованные профили. Этап ссылается на профиль целиком; если `model` отсутствует, применяется `defaultModel`. Поэтому при переходе на другую модель ей не достаётся `high` от предыдущей. Профиль без `variant` использует стандартный режим модели.

В OpenCode V2 effort выражается через вариант конкретной модели. Общего перечня вариантов и одинаковой стоимости у провайдеров нет. Перед запуском задачи runtime проверяет точную тройку «провайдер, модель, вариант»; недоступный `high` даёт ошибку с путём `models.careful.variant` и списком доступных вариантов. Молчаливой замены модели или effort нет.

Модель меняется на границе этапов в той же рабочей сессии. Runtime дожидается конца хода, вызывает `session.switchModel`, сверяет выбранную модель и вариант и лишь затем отправляет задание. В проходе этапа сохраняются запрошенный и подтверждённый профиль. Если пользователь вручную переключил модель, runtime сверяет выбор перед следующим управляемым ходом; ход с неподтверждённым профилем не засчитывается. Переключение и отправка задания не одна транзакция OpenCode: после сбоя runtime сверяет лог сессии, прежде чем отправлять ход повторно.

## Кто выполняет ручное тестирование

`manual-test` означает интерактивную проверку по шагам. У этапа обязателен явный `executor`. Сценарии, стенд, проверяемая версия и ожидаемые результаты одинаковы для обоих режимов:

| Конфиг этапа | Кто и как проверяет |
| --- | --- |
| `"executor": { "type": "human" }` | Runtime открывает панель со ссылкой на стенд, версией сборки и чек-листом без отметок. Пользователь выполняет шаги и отправляет результат в панели. Модель и `browserMcp` не указываются |
| `"executor": { "type": "agent", "browserMcp": "browse" }` | Рабочая сессия использует модель этапа и указанный браузерный MCP. `browse` здесь имя подключения проекта. Агент открывает стенд, выполняет шаги и перечитывает состояние страницы после действия. Для `keyboard-qa` он фиксирует значение поля после обновления страницы: одного успешного нажатия недостаточно |

Итог каждого сценария: «Прошёл», «Нашёл дефект» с фактическим результатом или «Не смог проверить» с причиной. Все сценарии прошли, значит исход `passed`. Найденный дефект даёт `failed`. Невозможность проверить (недоступен браузер, подключение или стенд) даёт `stuck`; исполнитель автоматически не меняется. Если в браузере нужен вход человека, пользователь завершает вход, а проверку продолжает агент; это не ответ на анкету и не результат теста.

Runtime записывает, кто выполнил проход. В режиме `agent` отчёт сдаёт рабочая сессия без человеческой формы. Заданные `before` и `after` в обоих режимах заполняет только человек в панели. Так можно поручить агенту всю проверку в браузере и отдельно запросить своё решение по отчёту.

Результат привязан к идентификатору сборки или отпечатку рабочей копии и версии сценариев. Если на стенд выложили другую сборку, старый результат для неё не принимается, повторная проверка начинает новый проход с пустыми отметками. Успешный `manual-test` не заменяет `verify` и одобрение диффа на `show`.

## Панель как обязательное условие перехода

Анкету создаёт runtime по определению этапа, даже если агент ни разу не вызвал инструмент вопроса. `before` открывается до первого задания модели, `after` после сдачи результата. Для незапланированного уточнения у рабочей сессии есть инструмент `request_input` с тем же представлением. Канал запросов к человеку один: панель. Текст «да» в чате не считается ответом и не двигает задачу.

Поле анкеты задаёт `type` (`choice`, `multiChoice`, `text`, `textarea` или `number`), подпись `label` и при необходимости пояснение `help`. У варианта `choice` может быть `recommended` с причиной; он показывается первым, но не выбирается за человека. На уровне анкеты `preview` указывает, какой результат показать, а runtime сам привязывает к нему версию.

В примере выше `visibleWhen` раскрывает замечания только при выборе «Переработать план», а `requiredWhen` не даёт отправить этот выбор без текста. Панель пересчитывает условия при смене выбора, runtime проверяет их заново при отправке. Если пользователь передумал и принял план, скрытое замечание не передаётся исполнителю.

1. Runtime сохраняет в одной транзакции вопрос, задачу, попытку, `stageRunID`, фазу, схему полей, preview и версию объекта решения; задача становится `waiting-user`. Уведомление главной сессии входит в ту же транзакцию.
2. Подключённый TUI показывает постоянную панель вопросов и сам открывает форму в главной или рабочей сессии. В форме видны задача, этап, точный объект решения и поля. Несколько вопросов образуют очередь, новая форма не затирает набранный ответ. Escape сворачивает форму до карточки «Требуется ответ», но не отвечает и не пропускает этап.
3. У двух окон один вопрос. При отправке runtime проверяет обязательные поля, допустимые значения, версию вопроса и основание решения. Первый валидный ответ и переход записываются вместе, второе окно показывает принятое решение. Повтор команды после обрыва возвращает прежний результат. Строка из пробелов не заполняет обязательное поле.
4. Если план или дифф изменился, пока форма была открыта, она помечается устаревшей, для новой версии нужен новый вопрос. Замечания при `repeat` уходят исполнителю вместе с адресом нового прохода.

Без открытого интерфейса панель не нарисовать. Гарантия такая: вопрос сохранён, этап стоит, при подключении TUI панель появляется сама. Плагин сначала читает открытые вопросы из runtime, затем обновляет их по событиям и повторной сверке; потеря события не теряет вопрос. CLI показывает, какие вопросы открыты и где ответить, но ответов не принимает. Молча перейти на чат нельзя даже при ошибке отрисовки.

Ответ принимается только через RPC-метод панели; инструментам моделей такой метод не регистрируется. Это защищает от случайного самоодобрения, а не от агента, который намеренно воспроизводит вызов панели через shell. Модель угроз и ограничения хука `execute.before` описаны в [архитектуре](architecture.md#права-и-защита).

## Как менять конфиг

Редактирование файла не требует пересборки. `opencode-orchestrator workflow validate <файл>` проверяет маршрут, `workflow explain <файл>` показывает развёрнутые этапы, модели, вопросы и переходы, `/orchestrate --workflow <имя> <ID>` выбирает маршрут для новой задачи.

При старте задачи runtime сохраняет развёрнутое определение и его хеш в SQLite. Инструкции, анкеты и профили разрешаются в этот снимок. Новые задачи получают новую версию файла, начатая задача переживает и правку, и переименование файла, и перезапуск на своей версии. Применение новой версии к уже идущей задаче отложено.

До назначения сессии загрузчик проверяет уникальность ID, известные виды и поля, ссылки на модели, ключи `on` и цели переходов, достижимость этапов и обязательные предпосылки `deliver`. В ошибке указывает путь в файле и причину: опечатка `befor` не должна тихо убрать обязательный опрос. Если провайдер временно недоступен, уже запущенная задача сохраняет этап и показывает причину ожидания.

## Что брать у OpenCode

На OpenCode 2.4.1 локальный `/openapi.json` подтверждает `POST /api/session/{sessionID}/model` и `Model.Ref` с `providerID`, `id` и необязательным `variant`, а также операции создания, чтения и ответа на формы сессии. Смена модели не проверяет, что модель существует, поэтому runtime сверяет её со списком `GET /api/model` сам. Наличие API форм не гарантирует автоматического открытия нужной панели, единого решения в двух сессиях и восстановления, к тому же `location/reload` отменяет ожидающие формы. Поэтому вопрос хранится в runtime, а TUI рисует своё представление. Нативную форму можно использовать для отображения, если опыт подтвердит эти свойства; её статус не становится вторым источником истины.

Первый проверяемый срез:

1. Запустить пример с тестовыми профилями из реального каталога. Разведку и план провести в одной сессии разными вариантами; неизвестный вариант останавливает запуск до первого платного хода.
2. Сдать план без вызова инструмента вопроса. Панель открывается сама. Ввести «одобряю» в чат, закрыть TUI, перезапустить runtime: код не начат, при входе открывается тот же вопрос.
3. Из панели вернуть план на исправление, затем принять новую версию из двух окон. Один принятый ответ, правильная версия плана, один запуск реализации.
4. Добавить этап `research` через файл и поменять ему модель. Новая задача видит изменение, начатая сохраняет свой снимок. Удалить обязательный `show`: загрузчик отклоняет маршрут.
