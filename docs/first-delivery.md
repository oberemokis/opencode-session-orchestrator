# Первая поставка

План реализации, согласованный 23 ноября 2026 года. Решения приняты на допросе и прошли опровержение по четырём линзам: корректность, откат и эксплуатация, объём, самоодобрение. Где этот документ расходится с [архитектурой](architecture.md), прав он, пока архитектура не обновлена.

## Цель и границы

Одна задача из свободного текста проходит маршрут `code` → `show` → `deliver` до локального коммита в ветке задачи. Человек отвечает в панели TUI. Задач несколько, мест три, лишние ждут в очереди. Рестарт runtime и рестарт службы OpenCode не теряют и не дублируют работу.

В первую поставку не входят:

- этапы `research`, `plan`, `review`, `verify`, `manual-test`, анкеты `before` и `after`, поле `when`;
- доставка `gitlab-mr`, ожидание CI, код-хост;
- чтение тикета из трекера (задача приходит текстом);
- хук `execute.before` (запись через MCP закрыта правилами сессии, см. Q29);
- список задач в TUI, передача владения главной сессией;
- ответы на вопросы вне TUI: из Desktop, веба и IDE пользователь видит сводку, но ответить не может;
- разные аккаунты одного MCP-сервиса для разных проектов, лимит мест на проект;
- команды CLI кроме `serve` и `status`;
- запуск через launchd или systemd, обычный `opencode serve` без `--service`;
- применение новой версии маршрута к идущей задаче;
- чистка worktree остановленных задач.

| # | Решение |

| Q1 | Цель: одна задача до local-commit, с панелью и переживанием рестарта runtime |
| Q2 | Несколько задач, очередь, три места на runtime |
| Q3 | Обычный TS и zod, без Effect |

| Q8 | Маршрут `code` → `show` → `deliver` (local-commit) |
| Q9 | Задача приходит текстом: `/orchestrate <текст>` |
| Q10 | Отчёт этапа берётся из истории сессии: вход вызова `stage_report` |
| Q11 | Хук отклонил коммит: исход `failed` с выводом хука, дальше по `on`. Хуки не обходятся |
| Q12 | После `done` worktree удаляется, ветка остаётся |
| Q13 | Защита статичным deny в правилах сессии. Хук `execute.before` отложен |

| Q17 | Маршрут из `.orchestrator/workflows/default.json`, загрузчик знает только поля первой поставки |
| Q18 | CLI: `serve` и `status` |
| Q19 | Коллизия ID сессии: `blocked`, в чужую сессию ничего не шлём |
| Q20 | Целевая версия OpenCode 2.4.1 |
| Q21 | Стоп: `/orchestrate stop <taskID>`, у модели инструмента остановки нет |
| Q22 | Два пакета: `opencode-orchestrator-runtime` (ядро в `src/core`, CLI как `bin`) и `opencode-orchestrator-plugin` |
| Q23 | Из `blocked` выводит вопрос в панели: новая попытка в том же worktree или стоп |
| Q24 | Хук изменил файлы при коммите: коммит откатывается, правки хука остаются в worktree, этап `failed`, затем снова `code` и `show` |
| Q25 | Задача помнит чат, из которого пришла, сводки идут туда. Стоп принимается из любого чата |
| Q26 | Worktree и ветка остановленной задачи остаются для разбора |
| Q27 | Главная сессия не защищена: deny только у рабочих сессий. Остаточный риск записан ниже |
| Q28 | Свежий worktree готовит runtime по `setup` из `.orchestrator/config.json`: копирует перечисленные файлы из главного checkout и запускает команду. Сбой даёт `blocked` с выводом |
| Q29 | В правилах рабочей сессии запрещены все MCP-инструменты, кроме списка чтения из `.orchestrator/config.json`; браузерные MCP запрещены |
| Q30 | Проект дописывает свои запреты полем `deny` в `.orchestrator/config.json` поверх общего списка |

Умолчания: `node:sqlite`, zod 4, плагин подключается по локальному пути в глобальном конфиге.

## Отвергнутые варианты

| Вариант | Почему нет |
| --- | --- |
| Effect 3 в runtime | Пользователь выбрал обычный TS: меньше слоёв для первой поставки |
| XState для переходов | Таблица в чистой функции перебирается табличными тестами, машина состояний добавляет зависимость без выигрыша |
| Runtime поднимает плагин или launchd | Плагин выгружается после часа простоя; автозапуск отложен, пока не доказан ручной |
| Своё продолжение хода при обычном `serve` | Гонка с автопродолжением сервера даёт двойной ход |
| Этап `plan` с анкетой в первой поставке | Тянет формы анкет; ядро проверяется и без него |
| Задача по ID тикета | Чтение трекера не проверяет ядро и подключается позже без правок перехода |
| Отчёт только через RPC плагина | Пока runtime лежит, отчёт теряется; история сессии хранит вход вызова даже при ошибке |
| `blocked` при отказе хука | Повторять `deliver` бессмысленно, а замечание линтера исполнитель чинит сам |
| Хранить worktree после `done` | Каталоги копятся, ветки достаточно |
| Хук `execute.before` сразу | Нужен для списков MCP-записи, которых нет; шаблоны shell ловит permission |
| Весь дифф одной простынёй или только путь к worktree | Простыня нечитаема, а без показа `reviewedTree` фиксирует дифф, которого человек не видел |
| Однострочное поле или текст в рабочий чат | Замечания не помещаются в строку; текст в чате обходит runtime и теряется при повторе |
| Маршрут, встроенный в код | Формат уже описан, встроенный маршрут потом выпиливать вместе с тестами |
| Новая попытка молча при коллизии ID | Прячет ошибку runtime или чужое вмешательство |
| Откат службы на 2.3.2 | Живой тест всё равно идёт против локальной 2.4.1 |
| Четыре пакета | У ядра один потребитель, CLI это две команды; граница ядра держится запретом импортов |
| Только `stop` из `blocked` | Три коллизии занимают все места до ручного стопа |
| Принять коммит, изменённый хуком | В ветку попадает то, чего человек не видел |
| Одна главная сессия на проект | Передача владения это отдельная форма без пользы для первой поставки |
| Удалять worktree при `stopped` | Остановку делают, когда модель ушла не туда; посмотреть результат важнее |
| Свой агент для главной сессии | Переключать чат пользователя на чужой агент дорого ради неслучайного сценария |
| Исполнитель сам готовит worktree | От подготовки зависит хук на `deliver`, который запускает runtime; копировать `.env` по просьбе модели значит отдать ей решение о секретах |
| Оставить запись через MCP открытой в первой поставке | При подключённых YouTrack и GitLab исполнитель может комментировать тикет, создать MR или перезапустить пайплайн, и правило «публикует только runtime» не держится |
| Вернуть хук `execute.before` ради MCP | Запрет всех MCP-инструментов, кроме списка чтения, выражается статикой в правилах сессии |
| Общий список запретов без дополнений проекта | Опасные команды у каждого проекта свои: публикация пакета, деплой, миграции на стенде |
| Команда ответа в CLI для пользователей без TUI | Модель с shell ответила бы через неё сама |
| Отключать подпись коммитов при коммите runtime | Обходит политику пользователя; вместо этого `serve` проверяет подпись при старте |

## Факты OpenCode 2.4.1

Собраны разведкой 23 ноября 2026 на локальной службе: OpenAPI, бандл в бинаре, `opencode.db`, только чтение. Пункты с пометкой «шаг 0» подтверждаются на шаге 0.

- Durable-лог `GET /api/experimental/session/{id}/log` в штатном serve пуст. Сверка идёт через `GET /api/session/{id}/message` (`limit`, `order`, `cursor`, `type`; ответ `{data, cursor:{previous,next}}`). Курсор это base64 от `{id, order, direction}`. Ассистентские сообщения дописываются на месте: части приходят к уже существующему `message_id`.
- `POST /api/session` с существующим `id` молча возвращает существующую сессию, каталог, агента и `metadata` не сравнивает. ID сессии начинается с `ses`, сообщения с `msg_`; порядок задаёт `seq`, а не ID.
- Повтор `prompt` и `synthetic` с тем же ID сообщения отбрасывается и после рестарта, первая запись выигрывает без сравнения текста. Тот же ID с другим типом или в другую сессию даёт 409.
- Автопродолжение только в `serve --service`: сервер дописывает сообщение с `metadata.notice: "restart"`, будит сессию, до 10 попыток, ход может повториться. `/api/session/active` автопродолжение не показывает.
- Вход вызова инструмента записывается (`running`, `time.ran`) до запуска обработчика. Ошибка обработчика даёт `error` со входом. Крах OpenCode посреди обработчика после рестарта даёт `error` с `type: "aborted"` и входом. Вызов, оборванный во время стрима входа или с битым JSON, хранит вход `{}`. Повтор моделью создаёт новую часть с новым `callID`. Часть: `{type: "tool", id, name, state: {status, input, error?}, time: {created, ran?, completed?}}` в `content[]` ассистентского сообщения.
- Плагинный RPC открыт по HTTP: `POST /api/rpc/{rpcID}/{method}`, обработчик не знает, кто звонит. `POST /api/session/{id}/command` выполняет колбэк команды без человека.
- Permission: действие `shell`, шаблон превращается в якорный регэксп (`*` → `.*`), берётся последнее совпавшее правило (`findLast`), без совпадения действие `ask`. Сканер режет `&&`, `;`, `|`, но не разворачивает `env`, `sh -c`, `git -C`. Правила из конфига дописываются в конец правил агента, поэтому глобальный `allow *` перебивает deny агента. Правила из `session.create({permissions})` идут после правил агента.
- Модель задаётся объектом `{providerID, id, variant}` и меняется `session.switchModel` между ходами.
- Нативные формы без многострочного поля, `POST /api/location/reload` их отменяет. Плагин выгружается после часа простоя.
- HTTP API OpenCode не даёт отдельному процессу вызвать инструмент подключённого MCP. Решения по внешним фактам runtime принимает только через прямое API сервиса и свой адаптер.

### Шаг 0

Проверено 23 ноября 2026 на изолированной `opencode serve --service` 2.4.1 (свои `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME`, снимок базы с учётными данными, настоящий глобальный конфиг пользователя) одноразовым плагином и HTTP-клиентом. Модель `openai/gpt-5.6-luna`.

- Адрес и пароль службы лежат в `$XDG_STATE_HOME/opencode/service.json` (`url`, `version`, `pid`, `password`). Авторизация Basic, пользователь `opencode`.
- Плагин: локальный каталог без `exports` в `package.json` отдаёт `server.ts`, `tui.ts`, `rpc.ts` по соглашению; TS грузится без сборки, правка файла перезагружает плагин. `ctx.agent.transform` с `update(id, …)` создаёт агента, если его нет. `ctx.command.transform` с `add` регистрирует команду. RPC зарегистрирован через `ctx.rpc.register` и вызывается только с `location[directory]`, без неё `rpc.unavailable`.
- Плагин живёт в процессе службы и грузится на каждую location из её конфига. В worktree, где `opencode.json` не отслеживается git, плагина и агента `orchestrator-worker` нет (404). Поэтому плагин подключается в глобальном конфиге пользователя (`plugins`), а не в проекте. После `kill -9` и подъёма службы плагин поднимается сам вместе с location, когда служба продолжает ход.
- Локальный MCP без `pool: true` запускает свой процесс на каждую location: три worktree дают три процесса `lean-ctx mcp`.
- Инструменты плагина и MCP по умолчанию доступны модели только через codemode-инструмент `execute` (`tools.stage_report({...})`), а вход внутреннего вызова попадает в `state.metadata.toolCalls` лишь после завершения. `stage_report` регистрируется с `options: {codemode: false}`, тогда в истории это прямая часть `stage_report` со входом.
- Команда: обработчик получает `{sessionID, prompt: {text}, delivery}`. Сама команда ничего не пишет в чат и хода модели не вызывает, отвечает пользователю обработчик.
- `synthetic` с `resume: false` ложится в inbox чата и доставляется со следующим ходом, хода модели не вызывает; с `resume: true` модель отвечает. Сводки в чат-источник идут с `resume: false`.
- Сообщение `idle` есть: `{type: "idle", outcome: "succeeded" | "failed" | "interrupted", error?}`; на один ход бывает больше одного `idle`. `POST /api/session/{id}/interrupt` даёт `idle` с `interrupted`. `DELETE /api/session/{id}` даёт 204, затем 404; удалённый ID создаётся заново.
- `POST /api/session/{id}/model` пишет сообщение `model-switched`, но модель не проверяет: несуществующая пара принимается. Runtime сверяет модель со списком `GET /api/model` до отправки задания.
- Имена действий в правилах: `shell` (ресурс это команда), `read`, `edit` (путь), `external_directory` (каталог с `/*`), MCP-инструмент `<сервер>_<инструмент>` с ресурсом `*`. Маска в действии работает: `YouTrack_*` deny и `YouTrack_get_current_user` allow оставляют модели один инструмент, остальные она не видит вовсе.
- Deny возвращает модели «Permission denied», ход продолжается. Ответ `reject` на запрос права, наоборот, обрывает шаг.
- На настоящем глобальном конфиге с `allow *` правила сессии отклоняют `git push origin main`, `git -C <wt> push`, `bash -c "git push"`, `env git push`, `git commit --no-verify`, правку `opencode.json` и запись файловым инструментом вне worktree. Запись в чужой каталог через shell (`echo x > /вне/worktree`) проходит: `external_directory` shell не проверяет.
- Не проверено, потому что allowlist оболочки запрещает tmux: `dialog.show` с многострочным полем и диффом на 3000 строк, связь TUI с серверной частью плагина. Проверяются на шаге 5 руками.

## Устройство

### `opencode-orchestrator-runtime`

Ядро `src/core`, чистый TS без часов, SQLite, git и OpenCode. oxlint запрещает в нём импорты `node:*` и остального `src/` (правило `no-restricted-imports` в `.oxlintrc.json`).

- Схема маршрута на zod, `strict`. Этап: `id`, `uses` (`code`, `show`, `deliver`), `model?` (`{providerID, id, variant?}`), `instructions?`, `on?`, `limits?` (`retries` по умолчанию 2, `stallMinutes` по умолчанию 30). У `deliver` поле `delivery: {type: "local-commit"}`. Проверки: уникальные `id`, `goto` на существующий этап, перед `deliver` стоит `show` без правящих этапов между ними, `goto:deliver` разрешён только из `show`. Ошибка содержит путь к полю.
- `decide(state, event) → {ok: true, state, intents} | {ok: false, error}`.
  - События: `accepted`, `slot-granted`, `session-confirmed`, `session-collision`, `stage-reported{outcome, summary}`, `turn-ended-without-report`, `stalled`, `answered{questionID, choice, text?, tree?}`, `commit-result{kind: "ok" | "hook-rejected" | "tree-mismatch", output?}`, `intent-failed{intent, error}`, `stop-requested`.
  - Намерения через outbox: `ensure-worktree`, `prepare-worktree`, `create-session`, `switch-model`, `send-prompt`, `notify-lead`, `commit`, `remove-worktree`, `abort-session`. Локальные записи (место, вопрос) делаются в той же транзакции.
  - Действия `on`: `next`, `repeat`, `stop`, `goto:<id>`, `escalate`. Без ключа `passed` ведёт к `next`, остальное к `escalate`. Автоматический возврат назад увеличивает счётчик этапа, на который вернулись; выбор человека счётчик не трогает. На исчерпании `retries` действие становится `escalate`.
  - Вход в `deliver` только при `reviewedTree`, равном текущему дереву, иначе `escalate`.
  - `show`: `approve` записывает дерево из вопроса, `changes-requested{text}` ведёт по `on` (по умолчанию на предыдущий правящий этап, текст в задании), `stop`.
  - `escalate`: `repeat` и `stop`; `next` есть везде, кроме `show` и `deliver`. `repeat` у `show` открывает новый вопрос по новому дереву.
  - `blocked`: вопрос с вариантами «новая попытка» и «стоп».
- ID: префиксы `ses_` и `msg_`, затем хеш от соли установки, `attemptID` и имени намерения.

Остальной runtime:

- Хранилище: `node:sqlite` в `$ORCHESTRATOR_STATE_DIR` (по умолчанию `~/.local/state/opencode-orchestrator/`). Таблицы `tasks` (текст, чат-источник, каталог проекта, снимок маршрута и хеш, статус, этап, счётчики, `reviewedTree`, `revision`), `attempts`, `stage_runs`, `questions` (с деревом объекта решения), `intents`, `commands`. Версия схемы в `PRAGMA user_version`; база новее кода не открывается; перед миграцией копия файла.
- Команды `task.start`, `task.stop`, `question.answer` несут `commandID`; повтор возвращает сохранённый результат. Ответ сверяется с `questionID` и деревом объекта, а не с `revision`.
- Executor исполняет outbox после транзакции с лимитом повторов и backoff. Перед повтором ищет результат: сессию по ID со сверкой каталога и `metadata`, сообщение по ID, worktree через `git worktree list --porcelain` и `prune`, коммит на ветке после базы.
- Сверка: тик раз в 15 секунд, при старте и по сигналу `/api/event`. Курсор не переходит через сообщение без `finish`, последнее сообщение перечитывается всегда. Ход окончен, когда есть законченное ассистентское сообщение или `idle`; после `notice: "restart"` сессия считается занятой до конца хода. На конце хода засчитывается последний `stage_report` текущего `stageRunID` с непустым входом; если его нет, этап получает `turn-ended-without-report` и исход `stuck`. Простой считается по `time_updated`; пока OpenCode недоступен, таймер стоит и после восстановления связи начинается заново.
- Конфиг проекта `.orchestrator/config.json` читается из главного checkout на `task.start`, снимок хранится в задаче: `base`, `branchPrefix`, `setup` (`copy`: пути файлов из главного checkout, `command`: команда подготовки), `deny` (дополнительные шаблоны shell), `mcpRead` (разрешённые MCP-инструменты чтения).
- Старт `serve`: проверка версии OpenCode (незнакомая мажорная или минорная версия означает отказ с объяснением) и проверка, что `git commit` в проекте не требует интерактивной подписи; при провале `serve` называет причину и не стартует.
- Git: worktree `<проект>/.worktrees/<taskID>`, ветка `<префикс>/<taskID>` от базы из конфига. Сразу после создания `prepare-worktree` копирует файлы `setup.copy` и запускает `setup.command` в worktree; сбой даёт `intent-failed` и `blocked` с выводом команды, задание исполнителю не уходит. Дерево снимается через временный индекс (`GIT_INDEX_FILE`, `git add -A`, `git write-tree`). Коммит: проверка, что `HEAD` равен базе, `git read-tree <reviewedTree>` в индекс worktree, `git commit` с хуками. Ошибка git (lock, сигнал) отличается от отказа хука. Если `HEAD^{tree}` не равен `reviewedTree`, `reset --soft` на базу и `tree-mismatch`. После `done` `git worktree remove --force`.
- RPC: HTTP поверх Unix-сокета `0600`. Методы `task.start`, `task.stop`, `status`, `question.get` (с диффом), `question.answer`. При старте пробное подключение: живой сокет означает отказ, `ECONNREFUSED` означает удалить файл.
- Маршрут читается на `task.start` из главного checkout; невалидный файл отклоняет только эту команду.
- CLI `bin`: `serve`, `status`.

### `opencode-orchestrator-plugin`

- Сервер: регистрирует агента `orchestrator-worker` (`mode: "primary"`, deny на `subagent`) и `/orchestrate` через `ctx.command.transform`. `/orchestrate <текст>` вызывает `task.start` с ID чата и `commandID` из ID сообщения. `/orchestrate stop <taskID>` вызывает `task.stop`. Без аргументов вызывается `status`. Команда хода модели не вызывает: обработчик отвечает в чат сообщением `synthetic` с `resume: false`, в том числе «runtime не запущен, запусти serve». Инструмент `stage_report{stageRunID, outcome: "passed" | "stuck", summary}` регистрируется с `codemode: false`, отвечает «принято» и в runtime не ходит. RPC-методы для TUI проксируют `question.*` в сокет. Плагин подключается в глобальном конфиге пользователя по локальному пути, иначе в worktree его нет.
- Правила рабочей сессии runtime передаёт в `session.create({permissions})`:
  - `shell` deny: `*git *push*`, `*git *merge*`, `*git *commit*`, `*git *config*`, `*--no-verify*`, `*opencode api*`, `*/api/rpc/*`, `*runtime.sock*`, `*state.db*`;
  - шаблоны `deny` из конфига проекта дописываются после общего списка;
  - на каждый MCP-сервер location (`GET /api/mcp`) правило `<сервер>_*` deny, затем allow на каждое имя из `mcpRead` в виде `<сервер>_<инструмент>`; браузерные MCP в `mcpRead` не попадают;
  - `edit` deny на `opencode.json`, `.opencode/*`;
  - `external_directory` deny на `*`.
- TUI: при старте запрашивает `question.get` и показывает открытые вопросы через `dialog.show`: список всех открытых вопросов с переключением между ними, раскрыт самый старый. Для `show` выводит список файлов со счётчиками, дифф выбранного файла и пометку изменений в `.orchestrator/`, `.opencode/`, `opencode.json` и каталоге хуков. Варианты: «одобрить», «нужны правки» с многострочным полем, «остановить». Escape сворачивает форму в карточку и ответа не отправляет. Открытый вопрос runtime дублирует сводкой в чат-источник.

## Остаточный риск

Главная сессия это обычный чат пользователя с его правами. Её модель может вызвать `question.answer` или `/orchestrate stop` через HTTP: RPC плагина и команды открыты любому клиенту и вызывающего не различают. Утверждение архитектуры «RPC-метод ответа регистрируется только для TUI» неверно. Для такого вызова модель должна найти `rpcID` и собрать запрос; это выходит за модель угроз «случайное самоодобрение».

Запреты статичны и перечислены явно. Опасная команда, которой нет ни в общем списке, ни в `deny` проекта, исполнителю доступна. Текст тикета или документа, прочитанный через MCP, может подтолкнуть модель к такой команде.

Shell пишет вне worktree без запроса: `external_directory` проверяет только файловые инструменты. MCP-сервер, подключённый после создания сессии, в её правила не попадает и открыт до следующей попытки.

## Реализация

Шаги 0–6 сделаны 23 ноября 2026. Где код разошёлся с планом выше, прав этот раздел.

- Состояние задачи хранится одним JSON в `tasks.state`, попытки и проходы этапа живут внутри него. Отдельных таблиц `attempts`, `stage_runs` и `questions` нет: вопрос задачи один, и открытые вопросы собираются из задач.
- К намерениям добавлено `snapshot-tree` с событием `tree-snapshotted`: вопрос `show` открывается только со снятым деревом. Событие `accepted` заменено функцией `createTask`, задача создаётся вместе с записью команды в одной транзакции.
- Задача, ушедшая в `blocked`, `done` или `stopped`, отменяет свои невыполненные намерения: после стопа задание в сессию не уходит.
- `@opencode/client` в runtime не используется: свой клиент на `fetch` знает только нужные эндпоинты, а поддельный OpenCode в тестах повторяет ровно их.
- Отсутствие агента `orchestrator-worker` в свежем worktree runtime ждёт до 30 секунд: новая location грузит плагин после первого запроса (проверено на живой службе), и сразу после `git worktree add` агента нет.
- `commandID` для `task.start` и `task.stop` плагин берёт случайным: ID сообщения обработчику команды не передаётся.
- Сверка идёт тиком раз в 15 секунд и при старте, подписки на `/api/event` нет.
- Отказ хука отличается от ошибки git по выводу: `index.lock`, `fatal:` и `Unable to create` считаются ошибкой git и повторяются, остальное считается отказом хука.
- `serve` проверяет подпись пробным `git commit` в пустом репозитории с глобальным конфигом пользователя, без терминала и с таймаутом 15 секунд. Конфиг конкретного проекта не проверяется.
- TUI собран на штатных диалогах `select`, `prompt` и `alert`: список вопросов, файлы со счётчиками и пометкой чувствительных путей, дифф файла, действия `ctrl+a`, `ctrl+r` и `ctrl+x`. Форма «нужны правки» использует `dialog.prompt`; многострочное ли это поле, проверяется руками (случай 30). Своя форма на `dialog.show` понадобится, если нет.
- Плагин читает каталог runtime из `ORCHESTRATOR_STATE_DIR` процесса OpenCode, а без неё берёт `~/.local/state/opencode-orchestrator`. Значит `serve` с другим каталогом плагин не увидит.

Проверено: случаи 1–28, 33–35 и 38–40 тестами, 29 живым прогоном на изолированной службе 2.4.1 с `openai/gpt-5.6-luna`, 31 на шаге 0 теми же правилами, 32 и 36 вручную через HTTP на той же службе. Случаи 30 и 37 (панель TUI) ждут ручной проверки в tmux.

### Чистка читаемости, 24 ноября 2026

Поведение не менялось, 56 прежних тестов остались в силе. Что изменилось в устройстве:

- Один тип результата `Result<T>`: `{ok: true, ...}` или `{ok: false, error}`. `Decision` это `Result<Step>`, поле `reject` исчезло, `Step` и `Decision` не дублируют друг друга.
- Действия `on` в файле остаются строками. Загрузчик маршрута разбирает их один раз в `Action` (`next`, `repeat`, `stop`, `escalate`, `goto{stageID}`, `goto-previous-code`), в состоянии задачи лежит уже разобранное значение. Переход выбирается по `kind` с `assertNever`. Исход этапа типизирован (`Outcome`), ответ человека тоже (`AnswerChoice`), неизвестный вариант service отклоняет до `decide`.
- `TaskState`, `Question` и `StageRun` выводятся из схемы zod `TaskStateSchema`, а не описаны рядом. Строка задачи проверяется схемой при каждом чтении. Если строка не проходит, runtime не стартует и называет ID задачи и поле (`CorruptStateError`); тихо пропустить задачу нельзя, потому что продолжить её тоже нельзя. Намерения в `intents.payload` схемой не проверяются: их пишет и читает один и тот же выпуск, а смена формы поднимает `SCHEMA_VERSION`.
- Ответы OpenCode проверяются схемами из `opencode-schemas.ts`. Описаны только читаемые поля, лишние допускаются. Несовпадение даёт `PermanentError`: повтор не изменит форму ответа, задача блокируется с текстом несовпадения. Создание сессии проверяет только `id` созданной, остальное runtime перечитывает сам. Схема части `stage_report` сверена с записанной спецификацией OpenAPI 2.4.1.
- Ответы runtime на RPC описаны в `rpc-contract.ts`. `callRuntime` принимает схему и проверяет ответ, плагин и CLI берут схемы оттуда, а не пишут свои копии и не приводят тип.
- Сверка сессий вынесена из `engine.ts` в `session-watcher.ts`, `PermanentError` лежит в своём файле.
- В тестах паузы `settle` заменены на `harness.quiet()` (дожать всё, что пора, и перечитать сессии). Реальное время осталось только в случае 18: там предмет проверки сам простой.
- Случай 29 после чистки пройден живьём 24 ноября 2026 на изолированной службе 2.4.1 с `openai/gpt-5.6-luna` (задача доведена до коммита за 21 секунду, после `kill -9` runtime дубля задания нет). Ответы настоящей службы разобрались новыми схемами. Ловушка запуска: пока вход OpenAI в базе просрочен, ход молча заканчивается за секунды ответом `provider.auth`, и задача уходит в `escalate` «без stage_report»; сначала проверять модель коротким запросом.

### Отчёты рабочих сессий, 25 ноября 2026

После первого живого прогона на проекте с рабочим репозиторием выяснилось, что главная сессия не показывает ни ход задачи, ни ответ `/orchestrate`. Причины и принятые решения.

Причины:

- TUI рисует синтетическое сообщение только через `description` и показывает его, а не `text`. `reply()` в плагине слал сообщение без `description`, а `note()` runtime слал ярлык `opencode-orchestrator`: пользователь не видел ни ответа команды, ни сводок «ждёт просмотра», «готова», «заблокирована», «остановлена».
- Слой команд TUI без `mode: "global"` не попадает в палитру и список слэш-команд: «Оркестратор: открытые вопросы» из README там, скорее всего, не появлялась (вывод по зонду в изолированном TUI, на живом экране пользователя не проверен).
- Списка задач и отчётов по ходу нет, а двойной `/orchestrate` с тем же текстом создаёт две задачи.

Решения (поставки по порядку, каждая отдельным коммитом, между ними проверка пользователем):

1. `description` с фразой в `reply()` и `note()` (длинная причина обрезается до 300 знаков), `mode: "global"` у слоя команд. Сделано.
2. Диалог «Оркестратор: задачи» по `status` с переходом на рабочую сессию (`ui.router.navigate`). Переход на сессию другого каталога проверен на зонде, на живом экране пользователя нет.
3. Отсечение дублей `/orchestrate` внутри `insertTask` под `serial`: ключ это каталог проекта и текст без регистра и со схлопнутыми пробелами, незавершённые статусы `queued`, `active`, `waiting`, `blocked`, обход флагом `--again`, который разбирает плагин.
4. Короткий отчёт по шаблону раз в минуту в `SessionWatcher` (по его тику, второго опроса нет), ключ события `part.id` плюс статус, кольцо около 50 отчётов на задачу в памяти runtime, необязательные поля в `TaskSummarySchema`.
5. Строка в подвале и переход плагина на `tui.tsx` (`jsx` в `tsconfig`, peerDependencies).
6. Блок в боковой панели (ширина больше 120 колонок).

Отвергнуто:

- Модель-писатель отчётов. У runtime нет вызова модели без сессии OpenCode: нужна временная сессия без инструментов, чистка осиротевших сессий, лимиты, а вывод инструментов попадает в промпт. Поле `reports.writer` в конфиге попало бы в снимок задачи и сломало бы откат на v0.1.0 (строгая схема). Вернёмся отдельной поставкой.
- Таблица `reports` в SQLite. Нужны миграция, курсор и `UNIQUE(task_id, last_message_id)`, а откат на v0.1.0 упирается в `SchemaTooNewError`. Блок восстанавливается после перезапуска TUI, а он runtime не трогает. Вернёмся вместе с боковой панелью, если отчёты понадобятся после перезапуска runtime.
- Push из серверной части плагина в TUI через `events.emit`. У runtime нет канала подписки, плагин создаётся на каждый worktree, `cleanup` серверной `setup` не подтверждён. TUI продолжает опрашивать раз в 5 секунд.
- Схлопывание повторных «заблокирована» одной задачи. Для него пришлось бы хранить причину в `TaskState` со строгой схемой, и откат стал бы дороже. Сводки ограничены только по длине `description`.
- Клик мышью по строке задачи и команда `/orchestrate open`.
