# OpenCode Orchestrator: архитектура

Проектное решение для TypeScript-харнеса на OpenCode V2 (целевая версия 2.4.1). Документ описывает целевую систему. Первая поставка реализует её часть: маршрут `code` → `show` → `deliver` до локального коммита; что в неё вошло, чем она отличается от этого текста и что проверено на живой службе, записано в [плане первой поставки](first-delivery.md). Решения опираются на [обзор похожих проектов](research/prior-art.md); там же собраны факты об OpenCode V2, на которые ссылается этот текст.

Встроенный маршрут `fleet-v1` переносит поведение `task-fleet` и `task-run`: отдельная сессия на задачу, согласование плана, показ проверенного диффа, доставка. Название маршрута не обозначает версию OpenCode.

## Пять решений

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Кто решает переходы | Runtime по правилам маршрута. Решения, закреплённые за человеком, принимает только человек в панели. Модели работают внутри этапа | Так устроены все живые оркестраторы; там, где переходы и одобрения выдаёт модель-лид, человек теряет контроль |
| Кто пишет состояние | Один отдельный процесс runtime с SQLite. Плагин тонкий и состояния не хранит | Плагин V2 создаётся на каждую location и может быть выгружен; долгие ожидания в нём не живут |
| Как отличить человека от модели | Защищаемся от случайного самоодобрения, а не от враждебного агента: у моделей нет инструмента ответа, опасные действия режут правила рабочей сессии (`deny` для shell, файлов вне worktree и MCP вне списка чтения); хук `execute.before` отложен | Строгой локальной изоляции не сделал никто; обещать её нельзя |
| Когда создаётся worktree | До сессии, по ID задачи, один на задачу и все её попытки | Сессию не нужно переносить между каталогами, разведка не идёт в общем checkout |
| Что завершает задачу | Внешний факт: принятый коммит, слитый MR. Реакции на события описаны данными в маршруте | Локальная запись не доказывает, что действие произошло |

## Что видит пользователь

Вызов `/orchestrate APP-12 APP-19` в обычном чате делает этот чат главной сессией проекта. Команда без аргументов показывает существующие назначения:

```text
APP-12  План       Ждёт тебя: согласовать план                [Ответить] [Открыть]
APP-19  Доставка   Ждёт CI: MR !47, коммит a83b17            [Открыть]
APP-23             В очереди: все три места заняты
```

Список строит runtime по сохранённым данным. Главная модель не читает чужие чаты, не угадывает прогресс и не принимает решений по задачам: она получает сводки и передаёт runtime команды пользователя. Если у проекта уже есть главная сессия, вызов из другого чата показывает список и предлагает в панели передать владение; молча второй главной сессии не появляется. В первой поставке владения нет: задача помнит чат, из которого пришла, и шлёт сводки туда, а `/orchestrate stop <taskID>` принимается из любого чата.

На каждую задачу назначается своя корневая рабочая сессия до начала разведки. Главная сессия передаёт ей ID или исходное поручение пользователя, не пересказывая. Только рабочая сессия читает тикет, комментарии, документацию и код, выясняет критерии и готовит план; после согласования она же его реализует. До назначения runtime может определить проект, проверить подключения, исключить дубль и занять место. Задача в очереди ждёт исполнителя, главный чат её не исследует.

Вопросы человеку появляются только в панели TUI. Ответить можно из главной или рабочей сессии: это одна запись вопроса, первый валидный ответ принимается, второе окно видит принятое решение. Текст «да» в чате ответом не считается.

## Два пакета

| Пакет | Контракт |
| --- | --- |
| `opencode-orchestrator-runtime` | Один долгоживущий процесс пользователя на машине службы OpenCode. Единственный писатель SQLite. Очередь и места, worktree, сессии OpenCode, сверка по тикам, позже адаптеры код-хоста. Ядро лежит в `src/core`: чистый TS без часов, SQLite, git и OpenCode (Biome запрещает там импорты `node:*` и остального `src/`). Схема и проверка маршрута, функция перехода: на входе состояние задачи и событие, на выходе новое состояние и намерения внешних действий либо причина отказа. Все правила переходов живут в ядре. CLI это `bin` того же пакета: `serve` и `status`, позже `questions`, `open`, `doctor`, `workflow validate/explain/schema`. Ответов на вопросы и изменения хода задачи из CLI нет |
| `opencode-orchestrator-plugin` | Серверная часть регистрирует `/orchestrate`, агента `orchestrator-worker` и инструмент `stage_report`. TUI-часть показывает панель вопросов, позже список задач. Обе обращаются к runtime через его Unix-сокет, состояния задач не хранят. Подключается в глобальном конфиге OpenCode, иначе в worktree задач его нет |

У ядра один потребитель, поэтому отдельный пакет ему не нужен: границу держит запрет импортов.

```text
главная сессия ─┐
рабочая сессия ─┼─ серверный плагин ──┐
TUI-панель ─────┘   (RPC)             ├─ runtime ── core
CLI ──────────────────────────────────┘    ├─ SQLite
                                            ├─ OpenCode V2: сессии, inbox, история сообщений
                                            └─ Git, код-хост
```

Runtime работает на той же машине, что и служба OpenCode, и слушает Unix-сокет в своём домашнем каталоге с правами `0600`. CLI запускается там же. TUI может работать на другой машине: она ходит к runtime через RPC серверного плагина и сокет не открывает. Работа CLI с удалённой машины отложена.

Runtime не зависит от того, загружен ли плагин. Сводки в главную сессию он отправляет сам через клиент OpenCode (`synthetic`), ожидания CI ведёт сам. Плагин нужен, только пока пользователь или модель что-то делают в сессии.

## Задача, попытка, этап

Задача отвечает на вопрос «почему идём или стоим». Её статус один из:

| Статус | Когда входим | Как выходим |
| --- | --- | --- |
| `queued` | Задачу приняли, места нет | Место освободилось, создана попытка |
| `running` | Рабочая сессия ведёт текущий этап | Этап сдан, открыт вопрос, зарегистрировано ожидание, стоп |
| `waiting-user` | Сохранён открытый вопрос человеку | Принят ответ на этот вопрос |
| `waiting-external` | Ждём проверяемого внешнего факта с ключом | Адаптер сообщил наблюдение, совпавшее по ключу |
| `blocked` | Дальше идти нельзя, сохранены причина и следующий шаг | Явное решение человека продолжить |
| `stopped` | Пользователь остановил работу | Явное возобновление |
| `done` | Последний этап маршрута успешен | Возврат тикета в работу открывает новую задачу со ссылкой на прежнюю |

Попытка это пара «рабочая сессия и номер попытки» внутри задачи. У неё своё техническое состояние `starting`: место занято, сессия ещё не подтверждена. Замена утраченной сессии создаёт новую попытку в той же задаче и том же worktree; прежняя попытка остаётся в истории и больше не может продвинуть задачу.

Проход этапа (`stageRunID`) заканчивается исходом: `passed`, `failed`, `changes-requested`, `stuck` или `stopped`. Имена исходов намеренно не совпадают со статусами задачи. Исход и правила маршрута core превращает в следующий этап, вопрос, ожидание или статус задачи.

Лимит по умолчанию: три попытки в состоянии `starting` или активные на один runtime, включая ожидающие ответа или CI. Главная сессия в лимит не входит. Место освобождается, когда задача становится `done` или `stopped`, а не при закрытии окна или конце хода модели.

## Виды этапа

Вид этапа задаёт исполнителя, разрешённые действия и смысл результата. Маршрут задаёт порядок, инструкции, модель и вопросы.

| Вид | Кто исполняет | Результат |
| --- | --- | --- |
| `research` | Рабочая сессия, только чтение | Отчёт с находками и ссылками. Покрывает разведку и пользовательские проверки без правок |
| `plan` | Рабочая сессия, только чтение | Версия плана с критериями, проверками и оценкой |
| `code` | Рабочая сессия, правка | Изменение рабочей копии |
| `review` | Рабочая сессия, только чтение, своя модель | Заключение и находки по отпечатку диффа |
| `verify` | Рабочая сессия | Результаты проверок по отпечатку диффа |
| `manual-test` | Человек в панели или агент через браузерный MCP | Наблюдение по каждому сценарию для конкретной сборки |
| `show` | Человек в панели | Решение по точному диффу; одобрение записывает `reviewedDiff` |
| `deliver` | Runtime | Коммит одобренного дерева, push в ветку задачи, MR, ожидание CI для SHA и слияния |

Ревью идёт в той же рабочей сессии отдельным этапом со своей моделью. Отдельная сессия-ревьюер отложена.

`done` наступает, когда успешен последний этап маршрута. Для маршрута с доставкой последним стоит `deliver`, и его успех означает внешний факт: для `local-commit` коммит существует и его дерево совпадает с `reviewedDiff`, для `gitlab-mr` MR слит, а CI прошёл для ожидаемого SHA. Слияние выполняет человек в код-хосте; runtime только наблюдает его. Исследовательский маршрут может закончиться этапом `research` без доставки. Маршрут, где `deliver` возможен без `show` по актуальному диффу, загрузчик отклоняет.

## Переходы и реакции

В маршруте один механизм переходов: карта `on` у этапа. Ключ это исход этапа или выбор в анкете, значение это действие.

```json
{
  "id": "verify",
  "uses": "verify",
  "on": {
    "failed": "goto:implement",
    "stuck": "escalate"
  },
  "limits": { "retries": 2, "stallMinutes": 30 }
}
```

Действия: `next`, `repeat`, `stop`, `goto:<id>`, `escalate`. `escalate` открывает человеку вопрос с причиной и вариантами продолжить, повторить или остановить. Ключи анкеты имеют вид `before.<поле>.<вариант>` или `after.<поле>.<вариант>`, например `after.decision.revise`. Без явного ключа `passed` ведёт к следующему этапу, остальные исходы к `escalate`.

Автоматический возврат назад считается повтором. При исчерпании `limits.retries` действие заменяется на `escalate`. `stuck` выставляет runtime, если в логе сессии нет движения дольше `stallMinutes` или исполнитель сообщил, что не может продолжить (например, недоступен стенд). Для `deliver` те же ключи покрывают внешние события: `ci-failed` может отправить исполнителю лог через `goto:implement`, `changes-requested` из ревью MR пересылает замечания.

Анкеты `before` и `after` блокируют начало этапа и принятие его результата. Их формат, модели этапов и ручное тестирование описаны в [настраиваемых маршрутах](workflows.md).

## Вопросы и ответы

Вопрос создаёт runtime в двух случаях: по определению этапа (`before`, `after`, `show`, подтверждение публикации на `deliver`, `escalate`) и по инструменту `request_input`, которым рабочая сессия просит незапланированное уточнение. В обоих случаях это одна запись: `questionID`, задача, попытка, `stageRunID`, схема полей, preview и версия объекта решения (план, отпечаток диффа, SHA). Вопрос, переход в `waiting-user` и уведомление главной сессии сохраняются одной транзакцией.

Пользователь видит ID задачи, одну фразу о результате, вопрос и 2–4 варианта с последствиями; рекомендованный первым. Если решается судьба текста, preview показывает его целиком. Escape сворачивает форму до карточки «Требуется ответ», но не отвечает.

Ответ принимается только через RPC-метод панели. При отправке runtime проверяет, что вопрос открыт, объект решения не изменился, поля валидны. Ответ и переход сохраняются одной транзакцией, затем runtime отправляет рабочей сессии адресное сообщение. Если план или дифф изменился, пока форма была открыта, она помечается устаревшей и нужен новый вопрос.

Без открытого интерфейса панель не нарисовать. Гарантия такая: вопрос сохранён, этап стоит, при подключении TUI панель появляется сама. CLI показывает, где ответить.

Встроенные запросы разрешений OpenCode остаются отдельными: одобрение плана не даёт права на инструмент.

## Права и защита

Модель угроз: исполнитель не враждебен, но может ошибиться, например принять «да» в чате за согласие или выполнить push по собственной инициативе. Изоляцию от процесса с произвольным shell того же пользователя харнес не обещает.

- Роли `orchestrator-lead` и `orchestrator-worker` имеют `mode: "primary"` и правило `{"action":"subagent","resource":"*","effect":"deny"}`.
- Инструменты моделей не включают ответ на вопрос, смену статуса задачи и одобрение. Но RPC плагина и команды открыты по HTTP любому клиенту службы и вызывающего не различают: модель главной сессии с shell может ответить на вопрос, собрав запрос сама. Это выходит за модель угроз «случайное самоодобрение» и записано как остаточный риск. Ответить можно только из TUI: в Desktop, вебе и IDE видна сводка в чате.
- Рабочая сессия получает правила в `session.create({permissions})`, они идут после правил агента и конфига и побеждают глобальный `allow *`: `deny` для `git push`, `merge`, `commit`, `config`, `--no-verify`, обращений к API OpenCode и каталогу runtime, шаблоны `deny` проекта из `.orchestrator/config.json`, правка `opencode.json` и `.opencode/`, `external_directory`, все MCP-инструменты по маске `<сервер>_*` с разрешением списка `mcpRead`. Шаблон shell проверяется по всей строке команды, поэтому `bash -c "git push"`, `env git push` и `git -C <wt> push` тоже отклоняются. Запись вне worktree через shell правила не ловят. Хук `execute.before` отложен.
- Публикацию (push, MR) выполняет только runtime на этапе `deliver`. Закрытие тикета и комментарии в трекере отложены.

## Worktree и сессия

Порядок запуска попытки:

1. В транзакции занять место, создать попытку в `starting`, сохранить заранее сгенерированные ID сессии и первого сообщения.
2. Создать или переиспользовать worktree `<проект>/.worktrees/<taskID>` своим git, ветка `<префикс>/<taskID>` от базы по умолчанию из профиля проекта. Подготовить его по `setup` из `.orchestrator/config.json`: скопировать перечисленные файлы из главного checkout (например `.env.local`) и выполнить команду подготовки. Сбой подготовки даёт `blocked` с выводом команды, задание исполнителю не уходит. Готовит worktree runtime, а не модель: от подготовки зависит хук на коммите, а решение копировать секреты остаётся за пользователем.
3. `client.session.create({ id, agent, location: { directory }, title, metadata: { orchestrator: { taskID, attemptID } } })` без `parentID`.
4. `prompt` с сохранённым ID сообщения. Попытка переходит в `running`.

Повтор ID сообщения в той же сессии OpenCode принимает один раз, повтор ID сессии подхватывает существующую. Поэтому после сбоя на любом шаге runtime повторяет шаги с теми же ID, не дублируя задание.

Если из тикета следует другая база, рабочая сессия сообщает это в отчёте этапа `research` или `plan`. Пока в ветке нет правок, runtime пересоздаёт ветку от новой базы в том же каталоге. Каталог и сессия не меняются, переноса сессии нет. Если правки уже есть, открывается вопрос человеку.

Модель этапа runtime переключает на границе этапов: дожидается конца хода, вызывает `session.switchModel`, сверяет выбранную модель и вариант и только затем отправляет задание.

## Наблюдение и восстановление

Runtime не полагается на поток событий. `event.subscribe` служит сигналом «пора перечитать»: он не хранит историю и обрывается при переполнении.

- Durable-лог `GET /api/experimental/session/{id}/log` в штатной службе 2.4.1 пуст, поэтому runtime читает историю `GET /api/session/{id}/message`. Ход закончен, когда после задания есть сообщение `idle`, за которым нет уведомления `notice: "restart"`. Отчёт этапа берётся из входа последнего вызова `stage_report` этого прохода: вход пишется в историю до запуска обработчика и сохраняется при ошибке и при крахе службы.
- Сверка по тикам (по умолчанию раз в 15 секунд) и при старте: незакрытые задачи, открытые вопросы, попытки, ожидания и намерения внешних действий сверяются с OpenCode и код-хостом.
- После рестарта службы OpenCode в режиме `serve --service` сервер сам продолжает прерванные сессии: дописывает сообщение с `notice: "restart"` и будит сессию. Runtime считает такую сессию занятой до конца хода и «продолжай» не отправляет. Обычный `opencode serve` без `--service` не поддерживается.
- Если сессия с ID попытки уже существует в другом каталоге или с чужой `metadata`, задача становится `blocked` и в эту сессию не уходит ни одного сообщения: `POST /api/session` с существующим ID молча возвращает существующую сессию.
- `POST /api/location/reload` отменяет ожидающие формы и разрешения OpenCode. Вопросы харнеса это не затрагивает, они живут в SQLite.
- Если рабочая сессия действительно утрачена, задача становится `blocked`, и человек выбирает: новая попытка с текущего этапа или стоп.

Команда изменения содержит `commandID`, адрес задачи и ожидаемую ревизию. Повтор `commandID` возвращает сохранённый результат, команда по старой ревизии отклоняется. Транзакция сохраняет состояние и намерения; сетевые вызовы идут после неё. Перед повтором внешнего действия runtime ищет его результат: MR по проекту, ветке и SHA, коммит по дереву.

## Что храним

| Запись | Зачем |
| --- | --- |
| Проект | Профиль: база, префикс ветки, код-хост, разрешённые MCP-операции, `leadSessionID` |
| Задача | ID, развёрнутый маршрут и его хеш, текущий этап, статус, причина, `revision` |
| Попытка | `attemptID`, ID сессии, ветка, worktree, состояние, курсор лога |
| Проход этапа | `stageRunID`, запрошенная и подтверждённая модель, исход, отчёт, число повторов |
| Вопрос | Схема полей, preview, версия объекта решения, статус, ответ |
| Доказательства | Согласованная версия плана, `verifiedDiff`, `reviewedDiff`, наблюдения ручных проверок со сборкой |
| Ожидания и действия | Ключ внешнего факта (инстанс, проект, MR, SHA, вид проверки), намерение действия, подтверждённый результат, исходящие сообщения с заранее заданными ID |

SQLite отвечает за ход работы и решения пользователя. За существование коммита, состояние MR и результат CI отвечают соответствующие системы.

## Внешние источники

Рабочая сессия читает тикеты, комментарии и справку через MCP-подключения OpenCode; добавление справочного источника не требует изменений харнеса. Runtime сам проверяет только те факты, по которым принимает решение: CI и слияние MR. Для GitLab это прямое API с токеном только на чтение, кроме создания MR. Детали в [разборе MCP-интеграций](mcp-integrations.md).

## Отложено

- Закрытие тикета и запись в трекер, вопрос продукту с ожиданием ответа в тикете.
- Учёт активного времени и его синхронизация с трекером.
- Отдельная сессия-ревьюер и параллельные ветки маршрута.
- Адаптеры внешних ADE (Herdr и другие); кнопка «Открыть» пока использует вкладки TUI.
- Работа CLI и runtime с удалённой машиной.
- Применение новой версии маршрута к уже идущей задаче.
- Несколько инстансов трекера или код-хоста с пересекающимися ID.

## Первый сквозной срез

1. Передать главной сессии два ID. У каждого тикета свой критерий, известный только из комментариев. Каждый исполнитель сам прочитал тикет и включил критерий в план; главная сессия тикеты и код не читала. Разные корневые `sessionID`, worktree созданы до сессий.
2. План `APP-12` одобрить из главной сессии, `APP-19` из рабочей. Каждый ответ получил только его исполнитель. «Да» в чате ничего не двигает.
3. На показе `APP-12` вернуть замечание. Исполнитель исправил, перепроверил и показал новый дифф; старое одобрение не допускает доставку.
4. Пока `APP-19` ждёт CI, перезапустить runtime, затем службу OpenCode. После этого те же сессии и основание ожидания, ни одного повторного задания, CI чужого SHA ничего не меняет.
5. Слить MR `APP-19` в код-хосте. Задача стала `done`, место освободилось, главная сессия получила итог без запроса статуса.
6. Исполнитель пытается выполнить `git push` в базовую ветку и вызвать MCP-запись в трекер: оба вызова отклонены хуком.
