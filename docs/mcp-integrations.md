# Внешние источники через MCP

Решение для `fleet-v1`, 20 ноября 2026, сверено с [архитектурой](architecture.md) 23 ноября. Для чтения тикетов, обсуждений и справки рабочей сессии достаточно MCP-подключений OpenCode. Отдельный адаптер в runtime нужен там, где по ответу внешней системы харнес сам принимает решение, например снимает ожидание CI при закрытом чате. Поэтому добавление базы знаний не должно требовать изменения ядра, а подключение нового код-хоста для автоматической доставки потребует проверки его контракта.

## Что проверено

| Основание | Что из него следует |
| --- | --- |
| [MCP в OpenCode V2](https://opencode.ai/docs/mcp-servers) | OpenCode поддерживает несколько именованных `mcp.servers`, локальный stdio и удалённый Streamable HTTP. Агенту доступны инструменты и чтение ресурсов по URI. У удалённых подключений есть OAuth; для разных инстансов или аккаунтов нужны отдельные имена. |
| Каталог инструментов этой сессии | YouTrack объявляет `get_issue`, `get_issue_comments`, `get_issue_fields_schema`. GitLab объявляет `get_merge_request`, `get_merge_request_pipelines`, `get_pipeline`. У `get_issue_comments` есть `offset`, лимит страницы не больше 10. В тех же каталогах есть запись: например, `update_issue` и `save_pipeline`. |
| [HTTP API OpenCode](https://opencode.ai/docs/api) и [сетевой клиент](https://opencode.ai/docs/build/client) | В опубликованном разделе MCP есть список серверов, управление подключениями и каталог ресурсов. Общего HTTP-метода для вызова произвольного инструмента подключённого сервера там не заявлено. Возможность вызвать инструмент из чата не доказывает, что тот же вызов и OAuth доступны отдельному процессу. |
| Спецификация MCP [tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) и [resources](https://modelcontextprotocol.io/specification/2025-11-25/server/resources), редакция 2025-11-25 | Сервер определяет набор операций и их схемы. Инструмент может вернуть структурированные данные, текст или ошибку внутри успешного протокольного ответа. Ресурсы и подписки опциональны. MCP не определяет, что такое тикет, MR или успешная доставка. |

Каталог и документация подтверждают доступную поверхность, но не права на конкретный проект, полноту ответа или совместимость фонового вызова с целевой службой OpenCode 2.4.1. HTTP API службы не даёт отдельному процессу вызвать инструмент подключённого MCP, поэтому решения по внешним фактам runtime принимает только через прямое API сервиса и свой адаптер. Для анализа реальные тикеты и MR не запрашивались. [Прогон первой реализации](research/acceptance-2026-11-20.md) проверил чтение двух тестовых MCP из рабочей сессии и восстановление ожидания CI через адаптер GitLab с подменой HTTP.

## Один пример от назначения до доставки

1. Пользователь вводит `/orchestrate APP-12`. По профилю проекта runtime знает, в каком YouTrack искать `APP-12` и с каким GitLab-проектом работать. Главная сессия передаёт исходный ID. До назначения исполнителя никто не собирает досье на задачу.
2. Рабочая сессия читает описание и комментарии через YouTrack. Если критерий находится в одиннадцатом комментарии, первой страницы недостаточно. При прерванном чтении исполнитель отмечает, что именно не удалось прочитать. Оценка «поле пусто» допустима только после успешного чтения поля.
3. Из тикета исполнитель переходит к указанной спецификации в проектной базе знаний. В план попадают нужный критерий, ссылка на комментарий и версия спецификации, если источник её отдаёт. Поиск помогает найти документ; совпадение заголовка не делает документ основанием решения. Если спецификация расходится с тикетом и выбор меняет план, исполнитель показывает человеку оба места и конкретный вопрос.
4. На `deliver` харнес уже знает проект, MR, ожидаемый коммит и какой пайплайн требует маршрут. Рабочая сессия может читать лог, чтобы объяснить падение. Для перехода runtime сам читает состояние у код-хоста. Реплика «починили, CI зелёный» в комментарии полезна как повод перепроверить, но не снимает ожидание.
5. Пока окно закрыто, проверка завершается. После рестарта runtime читает из SQLite незакрытое ожидание, заново проверяет нужный пайплайн и применяет один допустимый переход. Пользователь видит в карточке, какой проект, MR, SHA и результат стали основанием.

## Где проходит граница в коде

| Потребитель | Что читает и за что отвечает |
| --- | --- |
| Рабочая сессия OpenCode | Выбирает нужные источники для своей задачи. Использует разрешённые MCP-инструменты или ресурсы напрямую. Передаёт критерии и ссылки в результат этапа; главный чат получает краткую сводку. |
| Runtime | Хранит привязки проектов, регистрирует ожидания, вызывает адаптер для конкретной проверки, проверяет форму результата и сопоставляет его с действующим ожиданием. Вызов сети происходит вне транзакции SQLite. |
| Core | Получает уже нормализованный факт и текущее ожидание. Решает, можно ли перейти дальше. Не знает названий MCP-инструментов, токенов, URI сервера и способа повторного запроса. |
| Плагин и CLI | Показывают в карточке источник, время последней успешной проверки, причину ожидания и следующий шаг. Плагин связывает обращение с действующей сессией; CLI не заводит вторую копию интеграций. |

### Как подключать новый сервис

**Только для справки.** Например, команда подключает внутреннюю документацию как третий MCP-сервер. Достаточно настроить сервер в OpenCode, дать рабочей роли доступ к нужным операциям поиска и чтения и проверить их из каталога реального worktree. Сервер может предоставлять только инструменты, без `resources/list`. Новый пакет и миграция SQLite для этого не нужны.

**Для правила маршрута.** Профиль проекта задаёт назначение источника, его инстанс, внешний проект и обязательную операцию: например, «проверить CI этого MR». Адаптер принимает адрес объекта, а не поисковую фразу. Он возвращает либо наблюдение с проверяемыми полями, либо причину, по которой его нельзя получить. Смена GitLab на другой код-хост меняет привязку и адаптер. Правило в core меняется, только если команда меняет сам критерий успеха.

**Чтение в фоне.** Runtime проверяет CI и слияние MR через прямое API код-хоста, а не через MCP. Опубликованный HTTP API OpenCode не даёт отдельному процессу вызвать инструмент подключённого MCP-сервера, а второй MCP-клиент добавил бы своё управление соединением и авторизацией. Для GitLab это `/api/v4` с токеном runtime: на чтение для проверок, с правом создать MR для `deliver`. MCP остаётся у исполнителя. Посылать модели промпт «проверь CI» как фоновый механизм нельзя: после перезапуска нужен проверяемый ответ, независимый от пересказа модели.

Подключения OpenCode и привязки маршрута решают разные задачи. Первые задают, _как войти_ в сервис; вторые, _какой источник отвечает_ за конкретную задачу. Для двух YouTrack с одинаковым `APP-12` нужен ключ «инстанс + внешний проект + ID», для GitLab `!47` также недостаточно без инстанса и проекта. Если по вводу нельзя однозначно выбрать профиль, спрашиваем до назначения. В первой версии у проекта один трекер и один код-хост; несколько инстансов с пересекающимися ID отложены. Сессия работает в каталоге worktree, поэтому подключения берутся из конфигурации OpenCode этой ветки. Если ветка задачи меняет конфиг подключений, привязку источника автоматически не заменяем: одноимённый сервер может указывать на другой аккаунт.

## Что именно считать фактом

Для ожидания CI записываем ключ проверки: инстанс, проект, MR, ожидаемый полный SHA и вид проверки (например, пайплайн головы MR или базы после слияния). Если выбран конкретный пайплайн, сохраняем и его ID. Для пайплайна результата слияния нужен соответствующий SHA результата; его нельзя молча подменить SHA вершины ветки. При нескольких пайплайнах на одном SHA применяем правило проекта, а до его определения не выбираем произвольный зелёный.

Адаптер сверяет принадлежность пайплайна нужному объекту, читает статус и возвращает источник, ключ, состояние, ссылку и время чтения. Время изменения у провайдера и время нашего чтения различаются. Ответ с `isError: true`, недостающим SHA или незнакомым статусом не становится подтверждением. Источник может отдавать только текст: для справки этого достаточно; для автоматического перехода нужен проверяемый формат с обязательными полями.

SQLite сохраняет основание уже принятого решения, версию задачи и ключ незакрытого ожидания. Для плана это согласованный критерий и ссылка на источник, для доставки это наблюдение о конкретном пайплайне. Так можно объяснить вчерашнее решение даже после изменения тикета. Полные логи CI, история всех комментариев и учётные данные для этого не нужны. Кеш справочного документа можно показывать с датой чтения; он не подтверждает текущее состояние доставки.

## Сбои и повторная сверка

| Ситуация | Что увидит пользователь и что сделает runtime |
| --- | --- |
| Не отвечает необязательная база знаний | Исполнитель укажет, какой раздел пропущен. Остальная разведка продолжается, если критерии уже определены. |
| Требуется вход или нет прав на обязательный источник | Карточка называет подключение и недоступную операцию. Не делаем вывод «тикета нет», не переключаем аккаунт автоматически. После восстановления доступа повторяем чтение. |
| GitLab отвечает `429`, временно недоступен или запрос истёк | Остаётся `waiting-external` с причиной и временем последней проверки. Повторы с ограничением частоты на подключение; учитываем `Retry-After`, если он есть. Повторяем чтение, а не запуск пайплайна. |
| CI ещё работает, завершился ошибкой или статус неизвестен | Это три разных исхода. Первый оставляет ожидание, второй даёт исполнителю основание разбирать падение, третий требует выяснить статус. Ни один не подтверждает доставку. |
| Событие потерялось, пришло дважды или после смены SHA | Уведомление ускоряет повторное чтение, но само не завершает этап. При старте и без подписок runtime сверяет сохранённые ожидания. Перед записью в одной транзакции проверяет, что ожидание, попытка и ревизия всё ещё актуальны. |

Разведка по умолчанию использует права на чтение. Список инструментов, префикс `get_` и подсказка MCP `readOnlyHint` не ограничивают права учётной записи. Проект перечисляет разрешённые MCP-инструменты в поле `mcpRead` файла `.orchestrator/config.json` в виде `<сервер>_<инструмент>`. Runtime закрывает в правилах рабочей сессии каждый подключённый MCP-сервер маской `<сервер>_*` и открывает только этот список (см. [права и защиту](architecture.md#права-и-защита)); закрытые инструменты модель не видит вовсе, это проверено на живой службе с YouTrack и GitLab. Браузерные MCP в список не попадают. Хук `execute.before` для этого не нужен. MCP-сервер, подключённый после создания сессии, в её правила не попадает до следующей попытки. Где сервис позволяет, учётные данные выдаются только на чтение. Текст тикета, лога или документа не может разрешить публикацию, изменить привязку проекта или ответить за пользователя. Запись в трекер (комментарий, смена статуса, закрытие тикета) в первой версии отложена.

## В каком порядке проверять

1. **Разведка на двух источниках.** На тестовой задаче положить один критерий на вторую страницу комментариев YouTrack, другой в связанную спецификацию. Принять план, если оба основания видны со ссылками, их прочитала рабочая сессия, а в главной осталась сводка. Повторить после переноса в worktree.
2. **Одна фоновая проверка.** Через API GitLab прочитать один известный MR без модели и открытого TUI. Зафиксировать форму результата, проект, SHA, ID пайплайна и статус. Проверить также отказ в доступе и истёкший токен.
3. **Восстановление.** Зарегистрировать ожидание для нового SHA, остановить runtime, завершить CI и запустить runtime снова. Подать также зелёный результат старого SHA и дубль актуального наблюдения. Приёмка: один переход по нужному результату и ссылка на его источник.
4. **Второй проект (после первой версии).** Подключить другой инстанс с такими же короткими номерами тикета и MR. Чтение из чужого проекта не должно ни наполнить план, ни снять ожидание. Новый необязательный источник справки подключается без изменений в core.

Первый полезный результат для команды: исполнитель собирает план из нескольких реальных источников. Независимый наблюдатель CI можно добавить следующим шагом, когда проверен контракт код-хоста и есть транзакционное хранение ожиданий.
