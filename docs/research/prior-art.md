# Похожие проекты: OpenCode и другие агенты

Обзор собран 23 ноября 2026 года. Цель: понять, как другие оркестраторы кодовых агентов отвечают на пять решений, по которым расходились наши ранние документы (принятые решения записаны в [архитектуре](../architecture.md)):

1. Кто решает переходы между этапами: модель-оркестратор или детерминированный процесс.
2. Где живёт состояние задачи и кто его пишет.
3. Как отличить одобрение человека от вызова инструмента моделью.
4. Когда создаётся worktree относительно сессии агента.
5. Что считается концом задачи.

Источники: поиск по GitHub (`gh search repos`, список awesome-opencode), документация и changelog OpenCode, npm, публичные обсуждения, документация сторонних оркестраторов. Пометка «код» значит, что вывод проверен по исходникам, «README» значит, что он взят из документации проекта и в коде не проверялся. Ничего из этого не перепроверено запуском.

## Итог

- Живые оркестраторы не отдают переходы модели. Решает человек (Conductor) или детерминированный цикл, который опрашивает трекер, PR и CI (Agent Orchestrator, Symphony, Copilot, LoopTroop). Модель работает внутри этапа. Проекты, где переходы и одобрения выдаёт модель-лид (opencode-ensemble, opencode-swarm), как раз теряют контроль человека.
- Worktree везде создаётся до сессии, по ID задачи, и переиспользуется между попытками. Переноса сессии в другой каталог нет ни у кого.
- Долгоживущее состояние держит отдельный процесс (LoopTroop, skulk) или внешняя система (трекер, GitHub). По данным skulk, плагин OpenCode V2 для этого не годится из-за жизненного цикла location.
- Строгой локальной защиты «модель не может ответить за человека» нет ни у кого. Работающий минимум: у модели нет инструмента одобрения, ответ приходит только из интерфейса.
- Конец задачи почти везде внешний: слитый PR или терминальный статус в трекере.

## Проекты для OpenCode

### opencode-mission-control

<https://github.com/nigel-dev/opencode-mission-control>, 31★, последний коммит 21 ноября 2026. Только V2: `@opencode/client` и `@opencode/plugin` ^2.3.0. Версия 1.x на tmux снята.

Плагин: каждая задача (job) получает git worktree и отдельную сессию OpenCode на том же сервере. Есть план в виде DAG, merge train в интеграционную ветку с тестами после каждого слияния и PR через `gh`. В TUI индикатор в футере, секция в сайдбаре и дашборд по `<leader>j`.

| Вопрос    | Ответ                                                                                                                                                                                                                                                                                                              |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Переходы  | Задачу или план запускает модель главной сессии через `mc_launch` и `mc_plan`. Дальше работает детерминированный reconciler с циклом 5 секунд: зависимости, слияния, паузы на чекпоинтах (README, частично код)                                                                                                    |
| Состояние | JSON-файлы `~/.local/share/opencode-mission-control/<project>/state/{jobs,plan}.json` и `reports/<job>.json`. Пишет серверная часть плагина, TUI читает через plugin RPC (`src/rpc.ts`). Одна SSE-подписка плюс сверка каждые 10 секунд (код)                                                                      |
| Одобрение | Человек от модели не отличается. Кнопка `p` в TUI идёт через RPC-обработчик `approve`, а тот вызывает тот же `mc_plan_approve.execute()`, что доступен модели как инструмент (код, `src/lib/rpc-handlers.ts`). У рабочих сессий убран инструмент `question`, вопросы идут через `mc_report(blocked)` и `mc_answer` |
| Worktree  | Плагин создаёт его своим git до сессии, Worktree API OpenCode не использует. Затем `client.session.create({ location: { directory: worktreePath }, title, agent, model, metadata: { missionControl: { jobId, planId, launchSessionID } } })` без `parentID` (код, `src/lib/job-runtime.ts`)                        |
| Конец     | Ход завершён, отчёт не `blocked`, нет открытых вопросов и разрешений, нет незакоммиченных изменений. Конец плана: всё слито, тесты зелёные, PR создан. После рестарта сервера прерванной задаче один раз отправляется «продолжай» (README)                                                                         |

Что взять: код запуска и наблюдения за корневыми сессиями, TUI-часть через RPC. Чего избегать: состояние внутри плагина и одобрение, доступное модели.

### LoopTroop

<https://github.com/looptroop-ai/LoopTroop>, 182★, последний коммит 22 ноября 2026. `@opencode-ai/sdk` ^1.19.5 плюс собственный транспорт V2 (`server/opencode/v2Transport.ts`, `v2Mapping.ts`), версия определяется автоматически.

Локальный демон с веб-интерфейсом (Hono, SSE). Тикет проходит интервью, PRD (совет из нескольких моделей), разбивку на «beads», код в worktree, финальные тесты, ручной QA и PR.

| Вопрос    | Ответ                                                                                                                                                                                                                                                              |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Переходы  | Детерминированная машина XState 5, `server/machines/ticketMachine.ts`, около 33 состояний: от `DRAFT` через `WAITING_PRD_APPROVAL`, `CODING`, `RUNNING_FINAL_TEST`, `CREATING_PULL_REQUEST`, `WAITING_PR_REVIEW` до `COMPLETED`, `BLOCKED_ERROR`, `CANCELED` (код) |
| Состояние | SQLite через drizzle (`server/db/schema.ts`), снимки машины в `server/machines/persistence.ts`, артефакты в `.ticket/`. Пишет один процесс (код)                                                                                                                   |
| Одобрение | Человек нажимает в веб-интерфейсе, `approvalHandlers.ts` отправляет машине `APPROVE` или `APPROVE_EXECUTION_SETUP_PLAN`. У модели такого инструмента нет (код). Ворота: интервью, PRD, beads, настройка исполнения, PR                                             |
| Worktree  | Создаётся при инициализации тикета (`server/ticket/initialize.ts`), до сессий исполнения (код, порядок выведен по вызовам)                                                                                                                                         |
| Конец     | Конечные состояния машины, PR и его ревью. Упавший bead уходит в повтор со свежей сессией до исчерпания лимита (README)                                                                                                                                            |

Что взять: модель жизненного цикла тикета с явными состояниями ожидания одобрения и единственным писателем SQLite. Минусы для нас: интерфейс веб, а не TUI, V2 подключён поверх v1 SDK.

### skulk

<https://github.com/kitlangton/skulk>, 26★, последний push 13 октября 2026. Работает с V2 через `ctx.session.prompt`.

Демон под launchd или systemd плюс CLI. Будит сессию позже: по таймеру, `gh-run`, `pr-checks`, публикации в npm, завершению команды или изменению вывода опроса. Состояние в SQLite `~/.local/state/skulk/skulk.db`, пишет только демон. Одобрений и worktree нет.

Ценен раздел README «Why a daemon and not an OpenCode plugin» (по исходникам OpenCode не проверено):

- плагины V2 создаются отдельно на каждую location;
- простаивающую location выгружают через 60 минут;
- после рестарта сервера плагин не загружается, пока к его location никто не обратится.

Отсюда вывод автора: долгие ожидания в плагине не живут. Второй приём: ID сообщения сохраняется до отправки, повторный POST с тем же ID OpenCode принимает один раз.

### opencode-ensemble

<https://github.com/hueyexe/opencode-ensemble>, 269★, последний push 15 ноября 2026. v1 и V2 (`@opencode/plugin` 2.0.3).

Команды агентов: лид, тиммейты, доска задач, сообщения, worktree на тиммейта, веб-дашборд на порту 4747. Переходы решает модель-лид. Состояние в SQLite (WAL), пишут экземпляры плагина; при старте зависшие участники помечаются ошибкой, недоставленное доставляется заново. `plan_approval` одобряет лид-модель, не человек. Worktree создаётся при `team_spawn`, сессии, судя по `src/v2-session.ts`, дочерние. Конец: `team_tasks_complete`, затем `team_merge` и `team_cleanup` (README, код частично).

### opencode-workflow-engine

<https://github.com/pacmm255/opencode-workflow-engine>, 6★, последний push 12 сентября 2026. Только v1.

Сценарии из дочерних сессий с журналом и повтором, режим `/workflow-goal` с супервизором. Полезные идеи (README):

- ввод человека помечается в части сообщения `metadata: {"workflowOrigin":"human"}`, автоматика ставит `automation` или synthetic. Это договорённость о разметке, а не защита: метку может поставить любой, у кого есть доступ к API;
- аренда проекта не даёт двум экземплярам плагина запланировать одно и то же дважды;
- цель закрывается, когда каждому критерию соответствует свежее доказательство, а отпечаток рабочей копии совпадает до и после проверки.

### opencode-swarm (ZaxbyHub)

<https://github.com/ZaxbyHub/opencode-swarm>, 541★, последний push 23 ноября 2026. `@opencode-ai/sdk` ^1.18 и адаптер V2 в версии 7.x.

Модель-архитектор ведёт фазы, на каждом шаге ворота из моделей critic, reviewer и test_engineer, которые хуки плагина проверяют детерминированно. Состояние в файлах `.swarm/` (план, доказательства, области), переживает перезапуск. Человек участвует только подтверждением «Ready for Phase N+1?», которое режим `auto-proceed` отключает. Параллельные задачи идут в worktree (README).

### opencode-workflows

<https://github.com/rphang/opencode-workflows>, 3★, последний push 18 ноября 2026. Только V2 2.3.0.

Модель пишет JS-сценарий, который раздаёт работу субагентам, при необходимости с `isolation: 'worktree'`. Работает в фоне, ведёт журнал с `resumeFromRunId`, показывает дерево прогона в TUI и Desktop. Переходы задаёт сценарий от модели, сессии дочерние, одобрений нет (README).

## Оркестраторы для других агентов

### Agent Orchestrator

Бывший проект ComposioHQ, с июня 2026 у AgentWrapper. Версия v0.9.x nightly, один основной мейнтейнер. Поддерживает Claude Code, Codex, Cursor, Aider и OpenCode. Документация: mintlify.com/ComposioHQ/agent-orchestrator, README `@composio/ao-core`.

- Переходы детерминированные. LifecycleManager опрашивает агента и код-хост: `spawning → working → pr_open → ci_failed/review_pending/approved → mergeable → merged`. Опрос вместо вебхуков выбран сознательно, чтобы ничего не терять после рестарта.
- Состояние в плоских файлах `~/.agent-orchestrator/<id>`, без базы.
- Отдельного одобрения нет, человек одобряет PR. Автослияние по умолчанию выключено.
- Порядок запуска: проверка issue, `Workspace.create()`, запуск агента, запись метаданных.
- Конец: `merged`. Реакции описаны данными: `ci-failed` отдаёт агенту логи (до двух повторов), `changes-requested` пересылает комментарии и через 30 минут эскалирует человеку, `agent-stuck` уведомляет.

### Symphony (OpenAI)

<https://openai.com/index/open-source-codex-orchestration-symphony>, спецификация SPEC.md от апреля 2026, эталонная реализация на Elixir. Работает с Codex.

- Планировщик детерминированный и единственный меняет состояние расписания. Статус тикета обычно меняет сам агент своими инструментами.
- Истина в трекере (Linear). Состояние планировщика сознательно в памяти, таймеры повторов после рестарта не восстанавливаются.
- Одобрения нет. Прогон заканчивается в статусе передачи, например `Human Review`. Агент запускается с `--ask-for-approval never`.
- Каталог на issue создаётся при первом запуске и переиспользуется между попытками. Хуки `after_create`, `before_run`, `after_run`, `before_remove`.
- На каждом тике статус сверяется заново: терминальный останавливает работу и чистит workspace. Есть таймаут зависания и экспоненциальная задержка повторов.
- Маршрут и хуки лежат в `WORKFLOW.md` в репозитории проекта: YAML плюс шаблон промпта.

### Облачный агент GitHub Copilot

docs.github.com, раздел о рисках и мерах защиты. Самая продуманная защита одобрения из всех:

- тот, кто поставил задачу, не может одобрить PR;
- агент не может одобрить, слить или пометить PR готовым к ревью;
- CI не запускается, пока человек с правом записи не разрешит;
- пушить агент может только в одну ветку `copilot/*`.

Среда эфемерная, на каждую сессию, с лимитом 59 минут. Одна задача даёт один PR.

### Conductor

<https://www.conductor.build/docs>, macOS, закрытый код. Работает с Claude Code, Codex, Cursor и OpenCode. Решения принимает человек. Workspace со своей веткой создаётся из ветки, PR или issue до запуска агента. Просмотр диффа с комментариями, которые уходят обратно агенту, и вкладка проверок. Цикл: PR, слияние при одобрении и зелёном CI, архив.

### Остальное

- Kiro specs (<https://kiro.dev/docs/specs>): фиксированные фазы requirements, design, tasks с ревью артефакта перед следующей фазой. Состояние в файлах спецификации в репозитории.
- Codex cloud и Cursor cloud agents: setup-скрипт при создании контейнера, maintenance-скрипт при возобновлении из кеша. У Cursor много жалоб на облачных агентов, которые замирают и не доходят до терминального состояния.
- Claude Squad и uzi: tmux и worktree без переходов, человек сам ведёт цикл. Активность в 2026 не подтверждена.
- Sculptor (Imbue): контейнер на агента и синхронизация в рабочую копию по запросу.
- Закрылись или заброшены: Terragon (январь 2026), Crystal (февраль 2026, преемник Nimbalyst), Vibe Kanban как продукт (Bloop закрылась в апреле 2026, проект поддерживает сообщество), Roo Code Cloud (май 2026), Google Jules. Container Use от Dagger не выпускался с августа 2025.

## Факты об OpenCode V2

Из документации сервера (<https://opencode.ai/docs/server>), changelog 2.2.0 и 2.3.0 и `AGENTS.md` репозитория OpenCode. На нашей установке не проверялось.

- `POST /api/session/{id}/prompt` надёжно принимает ввод и будит исполнение, с `resume: false` только ставит в очередь. Прерывание через `/interrupt`. `GET /api/session/active` отдаёт активные сессии, `POST /api/experimental/session/{id}/wait` ждёт простоя.
- Повтор ID элемента inbox в той же сессии принимается один раз, payload повтора игнорируется. Повтор ID сессии подхватывает существующую.
- `GET /api/event` не хранит историю: медленный потребитель обрывает поток, пропущенное теряется. Для повтора есть `GET /api/experimental/session/{id}/log?after=<seq>&follow=true`, лог сессии по курсору. Маршрут экспериментальный.
- После рестарта сервер сам продолжает захваченные сессии, однократность не гарантируется. Если runtime в этот момент тоже отправит «продолжай», ход исполнится дважды.
- `POST /api/location/reload` отменяет все ожидающие разрешения и формы.
- Плагины грузятся асинхронно: сразу после старта списки агентов и моделей бывают пустыми, а действия падают с not found.
- В 2.3.0 появился хук `execute.before`, который может отклонить вызов инструмента через `Tool.Error`, экспериментальный `session.fork`, а субагенты по умолчанию стали фоновыми.
- С 2.2.0 TUI-плагины требуют OpenTUI 0.7.

Известные жалобы: сессии в `serve` зависают в busy, когда инструмент Task запускает субагента. После переименования `permission.updated` в `permission.asked` (1.1.1) сломались клиенты. Нет уведомления о том, что сессия встала на запросе разрешения.

## Выводы для нашей архитектуры

1. Переходы считает runtime по правилам маршрута, решения за человеком принимает только человек. Модель-оркестратор из раннего исследования не нужна: главная сессия показывает сводку и передаёт команды пользователя.
2. Состояние пишет один отдельный процесс с SQLite. Плагин остаётся тонким: связывает вызов с `sessionID`, показывает панель, передаёт команды. Это следует и из жизненного цикла плагинов V2, если подтвердится утверждение skulk.
3. Защищаемся от случайного самоодобрения, а не от враждебного агента. У моделей нет инструмента ответа, ответ принимается только из интерфейса. Хук `execute.before` режет push и merge в общие ветки и запись через MCP. В документах не обещаем изоляцию от агента с shell того же пользователя.
4. Worktree создаётся до сессии по ID задачи и переиспользуется между попытками. `session.move` и разведку в общем checkout убираем.
5. Конец задачи внешний: слитый MR или терминальный статус тикета. Реакции на события описываем данными в маршруте (`ci_failed`, `changes_requested`, `stuck` с лимитами и эскалацией) вместо нескольких механизмов переходов.
6. Восстановление строим на сверке по тикам и курсоре durable-лога, поток событий считаем сигналом к перечитыванию. ID сообщений генерируем детерминированно и сохраняем до отправки. Перед тем как будить сессию после рестарта, проверяем, не продолжил ли её сервер сам.
